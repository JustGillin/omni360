# Code Documentation

```DISCLAIMER```
The documents in this folder were generated by GPT Codex for the ORIGINAL X-Store project. AI generated docs are better than no docs, so they were kept.

**Read them with that in mind.** Omni360 is a fork, and the parts of X-Store these docs were written about - the Vimm's Lair search UI, 7z decompression, ISO extraction and the self-updater - have all been removed. The docs covering those features were deleted along with the code.

What remains is in three states, marked per-document below: **rewritten** for this fork and trustworthy, **still accurate** because it describes the networking and TLS layer inherited essentially intact, or **stale** and kept only because a partly-wrong description of the transport beats none. Where a document and the source disagree, the source is right.

The ATG framework under `Common/` is intentionally not documented in depth. It is Microsoft helper/sample code used for console rendering, input, resources, and related XDK support. The rest of the docs only mention ATG where the project calls into it.

## What this fork actually does

`main.cpp` mounts storage aliases, creates the console, brings up the drawn UI, then scans the console's own games folder - reading each title's ID, name and cover art straight out of its STFS package header (`StfsParser.cpp`), entirely offline. The list from last time (`LibraryCache.cpp`) is drawn immediately while that runs.

The app opens on **Home**: the games played most recently (`Recents.cpp`), the focused one's Xbox Live wallpaper filling the screen behind them, and a row of circular icon buttons across the top for the four places to go - **Games + Apps**, **Store**, **Queue** and **Settings**. **B** returns to Home from anywhere; **B** on Home asks whether to leave.

**Games + Apps** is the only page with a sidebar, and that sidebar is its own group's navigation rather than the app's: Games, and Apps, Homebrew or Emulators once each has folders. Every other page runs full width. On a game, **A** plays it and **X** opens its page, where **Find DLC** and **Title updates** authenticate to archive.org with an IAS3 access/secret key pair (`ArchiveOrgDLC.cpp`) and search a collection by fuzzy game-name match. A disc in the drive appears as the first tile on both Home and Games, and installs as Games on Demand (`DiscSource.cpp` reads the drive raw, `GodConvert.cpp` writes the package - no network involved).

- **DLC** comes from the `msx360gcdlc` item as `.rar` archives. Their member lists are read by walking the RAR header chain over small `Range` requests, and each wanted member is fetched through archive.org's virtual-path URL, which serves it already extracted - so nothing here decompresses RAR. Members land in `Content\0000000000000000\{TitleID}\{ContentType}\{ContentID}`. Avatar-item members are skipped.
- **Title updates** come from the `microsoft_xbox360_title-updates` item as `.zip` archives holding a single member. Its name is read from the zip's central directory and decides the destination: a lowercase `tu...` name installs under `{TitleID}\000B0000\`, an uppercase `TU_...` name into the console's `Cache` folder.

Networking still goes through `downloadFileHTTPS()` / `httpRequestHTTPS()` in `downloadFile.cpp`, which parses the URL, initializes XNet/Winsock, builds an `XboxTLSContext`, injects hardcoded trust anchors, resolves DNS, performs a BearSSL TLS 1.2 handshake, sends an HTTP/1.1 request, and streams the response into either a file or a memory buffer. That layer is inherited from X-Store essentially intact, which is why the networking docs above are still worth reading.

The project is built around console limitations: no normal OS certificate store, limited memory, FATX/FAT32 file-size limits, and Xbox path aliases such as `game:\`. Most of the custom glue exists to keep large downloads streaming rather than loading whole files into RAM.
